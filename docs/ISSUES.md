# Issues Found

These are product gaps and surprises found while building and running this demo against real Google Cloud. Project `my-demo-project`, region `us-east4`, October 2026. Exact requests and responses are in [ARCHITECTURE.md](ARCHITECTURE.md).

Status key:
- **Open:** a product gap, worked around in the demo.
- **Mitigated:** handled in the demo code.
- **Info:** behavior worth knowing.

| # | Area | Issue | Status | How the demo handles it |
|---|---|---|---|---|
| 1 | Ingress gateway | **The ingress gateway enforces content (Model Armor) only, not caller identity.** In `CLIENT_TO_AGENT` mode, Agent Gateway applies Model Armor (`CONTENT_AUTHZ`) policies to `query` / `streamQuery`, but it doesn't authorize callers by identity: an IAP `roles/iap.httpsResourceAccessor` grant on the orchestrator's registry entry had no effect (an ungranted service account still got HTTP 200 for 22+ minutes, with `iapPolicyVersion` V1 and V2, and no IAP decision was ever logged). The ingress gateway also writes no request logs to Cloud Logging. | Info (by design for `CLIENT_TO_AGENT`) | Scenario 5 has a single user calling the agent through the ingress gateway, and is about Model Armor: with the gateway attached a normal request goes through (governed); with Model Armor on, a prompt-injection / PII request is blocked with HTTP 403 before it reaches the agent. Who may call the agent is controlled by IAM on Agent Runtime (`roles/aiplatform.user`), not by the gateway. The gateway-log feature covers egress only. |
| 2 | Model Armor (egress) | Egress Model Armor screens **MCP `tools/call`** traffic but **not A2A** `message/send` traffic. A malicious A2A message to an allowed agent goes through. | Open | Simulator rule changed: on egress, only MCP edges become `blocked`. The scenario 6 talk track calls out the contrast. |
| 3 | IAM conditions for MCP tools | A tool-level condition on `iap.googleapis.com/mcp.toolName` must also allow the empty string (`'' in [...]`). Without it, `initialize` and `tools/list` are denied and the MCP session never starts. | Mitigated | `egress_allow` always adds `''`. The annotation-based form (`mcp.tool.isReadOnly`, from `readOnlyHint` in the registered tool spec) also works and is verified live; both forms ship as policies (`*-readonly` by name, `*-readonly-hints` by annotation). |
| 4 | Gateway bind/unbind time | A PATCH to `agentGatewayConfig` is a long-running operation that redeploys the agent container. Attaching egress took 5m11s; attaching or detaching ingress, or detaching egress, took about 2.5 minutes. While it runs, a GET on the engine still shows the old config. | Info | The UI shows the change as *pending* for up to `PENDING_SECONDS = 600`, and status reads the engine's operations. Use **Live with fallback**, or attach the gateway about 10 minutes before presenting. |
| 5 | PATCH semantics | The PATCH replaces the whole `agentGatewayConfig`. Sending one direction drops the other. | Mitigated | The `gateway_attach` handler always re-sends the direction it isn't changing. |
| 6 | Model Armor toggle time | Creating or deleting the Model Armor authz extension and policy pair takes about 4 minutes per gateway. | Info | The checkbox shows *pending*. Turn it on before the Model Armor segment. |
| 7 | Default-deny platform endpoints | Under default deny, an Agent Runtime agent needs about 25 Google API hostnames registered and allowed: plain, `.mtls`, regional `.rep`, and some gRPC `:443` forms. Otherwise the agent can't reach Gemini, sessions, logging or tracing. | Mitigated | `bootstrap` registers them and grants a project-wide principal set. See ARCHITECTURE.md (g). |
| 8 | TLS right after attach | The first call through the gateway right after an attach or a registration sometimes fails with `ssl/tls alert handshake failure`. | Info | Shown as `error`, not `denied`. Fallback mode replays it, and a re-probe clears it. |
| 9 | Cloud Run reserved paths | Cloud Run reserves paths ending in `z`, so `GET /healthz` on the deployed targets returns Google's 404 page. | Info | Nothing in the deploy path uses `/healthz`; it's only for local runs. Rename it to `/health` if you need an external health check. |
| 10 | Agent Registry and A2A cards | The registry accepted a2a-sdk 1.x agent cards, where the URL is in `supportedInterfaces[].url` with no top-level `url`, and the gateway matched the host correctly. Engines are registered automatically as agents. `gcloud agent-registry bindings` is for delegated OAuth, not the egress allowlist. | Info | Documented in ARCHITECTURE.md (a). |
| 11 | Billing API | `cloudbilling` `projects.getBillingInfo` returned 403 for a project Owner. | Mitigated | `preflight` falls back to `gcloud billing projects describe`. |
| 12 | Model Armor block responses | The block looks different on each path:<br>• **Egress MCP:** HTTP 403 with a JSON-RPC `result.isError` body that carries the template's custom message.<br>• **Ingress:** HTTP 403 `PERMISSION_DENIED`, "Model Armor: Prompt violates content security configurations".<br>• **Policy deny:** HTTP 403 with plain text `Egress request is not authorized.` | Info | The orchestrator's `classify_failure()` treats a 403 that mentions Model Armor (including the template's `agdemo-model-armor-block` message) as `blocked`, and any other 403 as `denied`. |
| 13 | Enforce vs dry run | There's no enforcement setting on the Agent Gateway itself. Enforce vs dry run is `iamEnforcementMode` (plus `failOpen`) in the metadata of the IAP authz extension that the gateway's REQUEST_AUTHZ policy points to. One extension can be referenced by policies on several gateways, so flipping it changes all of them. A gateway-level switch (or a per-policy mode) would match how admins think about it. | Open (product feedback) | `bootstrap` sets the mode from `gateways.iap_enforcement`. Policy Studio shows an Enforce / Dry run switch on each gateway: it updates the extension in place, or first gives that gateway its own copy of the extension when it's shared. Measured live (2026-10): a flip takes effect in about 2–3 minutes, sometimes before the operation reports done. |
| 14 | Ingress Model Armor from private clients | A VM with no external IP called an Agent Runtime agent privately (Private Google Access or a PSC endpoint for Google APIs, `REGION-aiplatform.googleapis.com`). The CLIENT_TO_AGENT gateway's Model Armor blocked only about 50–70% of identical injection prompts to the bound engine. Some calls to an *unbound* engine were also blocked, and blocking took about 12 min to fade after unbinding. Model Armor's own logs show it caught every prompt it was asked about; the missed requests never reached it. Enforcement seems to follow a project-and-region setting that spreads slowly, not the engine's binding. | Open (product feedback) | The demo doesn't support private ingress, and ingress Model Armor isn't presented as a guarantee. Details: policy-studio `docs/P0_FINDINGS.md` §T3. |
| 15 | Adding a connectivity template to an existing gateway | A one-step PATCH from no template to `agentConnectivityTemplate` fails ("an internal error has occurred", code 13, reproduced 4 times) and drops the gateway's labels. Two steps work: an inline `networkConfig` first, then the template (about 3.5 + 3 min). Google's VPC guide says to delete and recreate the gateway instead, which forces every agent in the project and region to be rebound. A template in use can't be edited, only swapped. | Open (product feedback) | The live demo's gateway was left unchanged. Private Networking mode uses a separate us-west1 gateway created with the template from the start. Policy Studio's audit (N3) gives the two-step guidance. |
| 16 | Agents behind a gateway get 401 | **Cause: a known google-auth bug, being fixed by Google.** An `AGENT_IDENTITY` engine with a newer google-auth gets 401 on its own Google API calls once bound to an Agent Gateway, with or without a connectivity template; the gateway log shows `iamcredentials.mtls.googleapis.com` ALLOWED with status 401. Seen first on the P0 test bed (template gateway, F44), then live 2026-10-21 (europe-west4, Internet mode): a new engine built from the Build it by hand page, which didn't pin google-auth, bound by PATCH to a plain `AGENT_TO_ANYWHERE` gateway. The demo's own engines never hit it because `deploy_spec.REQUIREMENTS` has pinned `google-auth==2.60.0` since the first commit. Workarounds: pin `google-auth==2.60.0`, or set `GOOGLE_API_PREVENT_AGENT_TOKEN_SHARING_FOR_GCP_SERVICES=false`, which opts out of the Context-Aware Access token binding (Google calls this strongly discouraged). | Workaround in place | The demo uses the pin only. It set the variable for a while (Private Networking themes from 2026-10-16, every engine on 2026-10-22); it was removed on 2026-10-22 and the live engines were updated in place. Verified live 2026-10-22 with the pin only: the privnet orchestrator, bound by PATCH to its template egress gateway, answered on the first prompt; its Gemini calls through the gateway returned 200. Drop the pin once Google ships the fix. |
